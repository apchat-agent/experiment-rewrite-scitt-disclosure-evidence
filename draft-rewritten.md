# Transformation Evidence and Coverage Reconciliation for Auditable Data Disclosure

draft-dogru-scitt-disclosure-evidence-04 — register rewrite of Abstract and Sections 1-9.

## Abstract

This document defines two evidence payloads for automated data access:
Transformation Evidence and Coverage Reconciliation.

An audit receipt shows that a gateway allowed an access. It does not show what
the gateway changed in the data before it sent the data out. It does not show
whether the set of receipts is complete against the data source's own record of
its activity.

Transformation Evidence is one statement for one disclosure. It gives the
classes of values that the gateway changed. For each class it gives the action
that the gateway applied and how many values it changed. It gives class names
and counts. It does not give values.

Coverage Reconciliation compares two records of the same time window. The first
record is the data source's own activity counters, read at the start of the
window and again at the end. The second record is the set of receipts for that
window. One client request can cause more than one source-level statement, so
the operator declares the correspondence to expect. Coverage Reconciliation then
puts each item into exactly one of five outcomes. The outcomes are: matched,
observed-without-receipt, receipted-without-observation, excluded, and
indeterminate.

The result does not report a plain "pass" and nothing else. It always reports
the five counts. Each bound that the comparison uses comes from one of four
places. The protocol defines it, someone measured it, the operator declared it,
or nobody declared it. The result gives that place for each bound it used.

The two payloads go into Signed Statements on a Transparency Service, as the
SCITT architecture describes. This document defines no receipt format, no
transparency mechanism and no signature format.

## 1. Introduction

Some systems put a policy gateway between an automated client and a data source.
An AI assistant is one such client. More and more of these systems emit access
receipts that are signed and hash-chained. Several receipt formats exist. All of
them share one property, and that property limits what a receipt can prove. The
party that performed the access also produces the receipt, and the receipt
covers an event that the same party chose to record.

Two gaps follow from that property.

First, a receipt usually states that an access happened. It usually states which
policy decision allowed the access. It does not state what happened to the data
between the Data Source and the client. A gateway may mask, redact, or tokenize
values before it discloses them. The operator makes a privacy claim, and that
transformation is what the claim is about. A conventional receipt does not
describe it.

An auditor who reads such a receipt learns that a client read a table. The
auditor does not learn whether the protected columns in that table left the
gateway transformed or unchanged.

Second, a receipt set covers only the accesses that produced receipts. Good
chaining and anchoring do not change this. A client can reach the Data Source
without going through the gateway. Such an access produces no receipt, and no
property of the receipt chain reveals it.

A hash chain detects the removal or the reordering of records that exist. It
says nothing about records that nobody created. Completeness therefore needs a
second account of the activity, and a party other than the gateway must produce
that account: the Data Source itself.

This document defines two evidence structures that address these gaps:

*  Transformation Evidence (Section 3): a statement bound to a single
   Disclosure. It states which classes of values the gateway transformed before
   the Disclosure. For each class it states the action the gateway applied and
   the count of values. It never carries the values themselves.

*  Coverage Reconciliation (Section 4): a procedure and a signed result
   statement. The procedure takes snapshots of a Data Source's own activity
   counters at the two ends of a time window. It compares those snapshots
   against the receipt set for that window. The result statement gives an
   outcome for each item of either account.

   The comparison runs between two populations, and it assumes neither of them
   to be complete. It runs under a correspondence that the operator declares
   (Section 4.4). The result distinguishes what was matched from what was
   observed without a receipt, receipted without an observation, excluded
   before comparison, or left undecided.

Both structures are payloads. They are intended to travel in Signed Statements
and to be registered on a Transparency Service, as the SCITT architecture
[RFC9943] describes. That architecture supplies append-only registration that a
third party can audit. This document deliberately does not reinvent it. This
document defines no new receipt format, no policy evaluation semantics, and no
transparency mechanism.

### 1.1. What these structures do not claim

Both structures follow one discipline: each states the limits of its own
evidence. Transformation Evidence describes what one Disclosure exposes. It
does not claim that a client cannot learn a value. It is the Issuer's signed
assertion that a transformation was applied, and it is not proof that the
transformation was applied (Section 3.4).

A Coverage Reconciliation result may report activity for which no receipt
exists. Such a report is a statement about missing evidence. It is not proof of
intent and not proof of a breach, and it MUST NOT be presented as either
(Section 4.7).

Neither structure reports a plain "pass" and nothing else. A reconciliation runs
against a correspondence that the operator declares. Its outcome carries no more
weight than that declaration (Section 4.4). Where the evidence does not decide
an outcome, the result reports the item as undecided. The result does not fold
that item into a proportion.

## 2. Conventions and Definitions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when,
and only when, they appear in all capitals, as shown here.

This document uses the following terms throughout:

Data Source:  The system that holds the data. It keeps its own account of query
   or access activity, for example a database's statement statistics.

Gateway:  The component between an automated client and a Data Source. It
   mediates access, applies policy, transforms results, and emits receipts.

Disclosure:  A single delivery of data from the Gateway to a client. The Gateway
   may have transformed that data.

Receipt:  A signed record of a Disclosure that the Gateway produces. This
   document works with any receipt format.

Protected Class:  A named category of values that policy subjects to
   transformation, for example "email", "national-id", "phone".

Window:  A time interval over which a reconciler performs reconciliation. Two
   snapshots of the Data Source's activity counters bound the interval. The Data
   Source stamps both bounds. Whether a Receipt falls inside those bounds
   depends on a second clock, the Gateway's (Section 4.3).

Mapping Profile:  A versioned statement that the operator declares. One
   client-level operation produces source-level activity, and the profile
   states the correspondence to expect between the two. The profile gives the
   bound on that multiplicity.

   It gives the clock that each side uses and the skew bound between the two
   clocks. It gives the rules that remove activity from the comparison. A
   Mapping Profile is a declaration about a deployment. The Gateway does not
   measure it (Section 4.4).

## 3. Transformation Evidence

### 3.1. Purpose

Transformation Evidence answers three questions for one Disclosure. Which
Protected Classes did the Gateway transform in the disclosed result? By which
action? In what count? The structure exists so that the transformation claim
becomes a signed artifact that anyone can register, instead of prose in an
operator's documentation.

### 3.2. Structure

Transformation Evidence is a JSON object with the following members:

v:  Structure version string. For this document: transformation-evidence/1.

disclosure:  A digest that binds this evidence to exactly one Disclosure. The
   digest is computed over the receipt for that Disclosure. Where the receipt
   format defines a canonical record hash, the digest is computed over that
   hash. Section 3.3 defines the digest form.

request:  A digest of the request that produced the Disclosure. The member holds
   the digest of the request and never the request text, because query text can
   itself contain protected values.

policy:  An object with two members. The member id identifies the policy version
   that the Gateway applied. The member decision gives the policy outcome under
   which the Disclosure proceeded.

classes:  An array of objects. The array holds one object for each Protected
   Class that the applied policy recognizes and that occurred in the disclosed
   result. Each object has:

   class:  The Protected Class name, as the policy names it.

   action:  One of mask, redact, tokenize, truncate, or none. The value none
      states that values of the class occurred and left the Gateway
      untransformed. Some deployments need to make that honest statement.

   count:  The number of values of this class in the disclosed result to which
      the Gateway applied the action.

The structure MUST NOT carry data values, transformed or otherwise. Only class
names, action names, counts, digests, and identifiers appear. An implementation
that encounters a value in a field defined here MUST reject the structure.

### 3.3. Serialization and digests

To digest and sign the structure, an implementation serializes it with the JSON
Canonicalization Scheme [RFC8785]. Digests in this document are SHA-256. An
implementation writes them as strings with the prefix sha256: followed by
lowercase hexadecimal. Future documents may register other digest prefixes. An
implementation MUST reject a digest whose prefix it does not recognize, instead
of guessing which form the digest has.

The same data model is expected to get a CBOR/COSE serialization [RFC9052], once
the JSON model has had review. Nothing in the model depends on JSON.

### 3.4. What Transformation Evidence does not prove

Transformation Evidence describes what one result exposes. It does not state
that a value of a Protected Class is beyond the client's reach. Consider a
request language that permits tests on protected columns. An allowed request
can then answer a question about a masked value, and the Gateway never
discloses the value itself.

A result count of one rather than zero gives the client one bit of the value.
Transformation Evidence for such a Disclosure is accurate, because the Gateway
did transform the value in the result. The client can still have learned
something about the value.

Consumers MUST NOT present Transformation Evidence as proof of non-exposure.
The evidence is also not proof that the Gateway applied the transformation: the
payload is the Issuer's signed assertion that the Gateway applied it. A
Verifier can establish on its own that the disclosed bytes carry the
transformation the Issuer describes. Without that independent check, the
evidence available shows what the named Issuer asserted and nothing more.

Where the Issuer is the Gateway that performed the transformation, the
assertion is about the asserting party's own work. A consumer who treats
such an assertion as verified has dropped the Issuer out of the trust statement
and has put nothing in its place.

Some deployments require that a class stays beyond the client's reach, and not
merely that its values are hidden. Such a deployment must enforce that
requirement in policy. For example, it can refuse access to the objects that
carry the class at all. No evidence structure replaces that enforcement.

The classes array covers only what the applied policy recognizes. The evidence
gives no count for a value whose class the policy does not name. A class that is
absent from the array therefore says as much about the policy's vocabulary as it
says about the data. It MUST be read that way.

## 4. Coverage Reconciliation

### 4.1. Purpose

Coverage Reconciliation answers one question for one Window. Did the Data
Source's own account record activity for which no Receipt exists? The mechanism
makes two conditions detectable that are otherwise invisible: a client went
around the gateway, and the receipt sink failed.

The essential property is that the two accounts under comparison come from
different components. The receipt set comes from the Gateway. The activity
counters come from the Data Source. A Gateway does not produce the Data Source's
account, so it cannot make activity that went around it disappear from that
account.

### 4.2. Activity snapshots

A snapshot is a JSON object that captures the Data Source's cumulative activity
counters at a point in time:

v:  Snapshot version string. For this document: activity-snapshot/1.

ts:  The time at which the reconciler took the snapshot (ISO 8601).

source:  An identifier of the Data Source and of the accounting scope inside it,
   for example the database role whose activity the counters cover. Both
   snapshots of a Window MUST carry the same source. A mismatch invalidates the
   Window.

entries:  An array of objects. The array holds one object for each activity
   pattern that the Data Source's account distinguishes. Each object has:

   pattern:  A digest of the normalized activity pattern, for example a
      normalized statement with the constants removed. The member holds the
      digest and not necessarily the text, because pattern text can embed
      protected values and schema detail. Deployments MAY keep pattern text
      privately for diagnosis. Only the digest is required here.

   count:  The cumulative counter value for this pattern at ts.

### 4.3. Reconciliation procedure

A reconciler takes a start snapshot, an end snapshot, and the receipt set for
the Window. It then proceeds as follows.

The reconciler checks the validity of the Window first. The two snapshots MUST
carry the same v and the same source. The end ts MUST be later than the start
ts. No pattern's counter may be lower at the end than at the start.

A counter that falls means that something reset or altered the Data Source's
account inside the Window. The Window is then unreliable. The reconciler MUST
report failure for the Window as a whole, instead of reconciling the patterns
that survived. An attacker who can reset counters must get an error and not a
clean report.

Membership of the Window is itself a bound, and two clocks decide it. The Data
Source takes the snapshot timestamps. The Gateway writes a Receipt's timestamp.
A reconciler could admit Receipts on an exact comparison between the two
timestamps. That rule then fails in one direction only.

Suppose the Gateway clock runs behind the Data Source clock. A Receipt that
names an object then falls outside the Window. The object that Receipt would
have accounted for then becomes activity for which no Receipt exists. That
outcome is the one whose meaning names gateway bypass (Section 4.7). A clock
difference of seconds can therefore produce the accusation when no real gap
exists.

In the case where someone found this problem, the measured difference was three
seconds. Nothing in the procedure sets a floor below which the problem stops
happening. A smaller difference is correspondingly harder for a reader to
suspect.

A Mapping Profile therefore declares which clock each side uses. It also
declares the skew bound between the two clocks. It declares both in the same
way that it declares multiplicity (Section 4.4). The profile digest covers
both, as it covers every other part of the profile.

Where nobody declares the skew bound, the rule below applies: the affected
items are indeterminate, and the result does not report them as missing
evidence. Suppose instead that the operator declares the bound, and a Receipt
falls further outside the Window than the bound allows. The Window boundary
then does not explain that Receipt. The item takes the outcome it would
otherwise have had, and a reconciler MUST report which bound it applied to
reach that outcome.

The reconciler then takes each pattern whose counter increased during the
Window. It attributes the pattern to the data objects the pattern touches. It
checks whether any Receipt in the Window names those objects. The reconciler
matches per pattern and per data object, and not per call count.

One client-level request may legitimately produce more than one source-level
statement. Call counts and receipt counts MUST NOT be compared one-to-one. A
reconciler may fail to determine which objects a pattern targets. Such a
pattern MUST NOT be silently ignored, and it receives the indeterminate outcome
below.

The comparison runs between two populations: source-level activity and Receipts.
It assumes neither population to be complete. Each item in either population
receives exactly one of the following outcomes:

matched: The item corresponds to an item in the other population. The
   correspondence holds within the bounds of the applicable Mapping Profile
   (Section 4.4), and within the Window. The profile's two kinds of bound do
   not act alike here.

   A multiplicity bound admits items to this outcome, and the skew bound does
   not. A Receipt outside the Window is never matched, however small the
   declared skew. The skew bound qualifies how far a reader can trust the
   boundary. It does not move the boundary.

observed-without-receipt:  The Data Source recorded activity against an object
   that no Receipt in the Window names.

receipted-without-observation:  A Receipt in the Window names an object for
   which the Data Source's counters record no activity.

excluded:  A rule stated in the Mapping Profile removed the item from the
   comparison before matching (Section 4.5).

indeterminate: The evidence or the Mapping Profile does not determine an
   outcome. Any one of the following gives this outcome. The reconciler could
   not attribute the pattern's objects.

   A required multiplicity or skew bound is undeclared. The item's only naming
   Receipt falls outside the Window. The Window's evidence does not suffice to
   decide.

An implementation MUST NOT report an item as matched when the outcome is
indeterminate. A missing decision is not a decision. Consider in particular a
Mapping Profile that does not declare the multiplicity bound the comparison
requires. The affected items are then indeterminate, and they are not clean
coverage.

The same rule binds the bound in time, in the opposite direction. An item may
leave objects unaccounted for. Suppose a Receipt outside the Window names every
one of those objects. The item is then indeterminate, and an implementation
MUST NOT report it as observed-without-receipt.

A reconciler cannot tell a Gateway clock that runs behind the Data Source from
a Receipt written late. A report of missing evidence would assert a distinction
that the reconciler did not make. This rule does not affect an item that leaves
even one object named by no Receipt at all. That is a genuine absence, and a
neighbouring object's clock does not make it undecidable.

Here, indeterminate does not mean a weaker pass. The comparison did not come out
clean, and a result statement MUST carry the outcome and the offset that
produced it. What the implementation is forbidden to do is to state the cause.

A reconciliation may produce no observed-without-receipt items. It then
establishes this much, under the declared correspondence: a Receipt that names
the same object exists for each observed source-level item. It does not
establish that every source-level statement had a Receipt of its own. A result
MUST NOT be stated in terms that assert that. One Receipt that names an
object can clear any number of further statements against that object inside the
Window. The procedure has then established attribution to the object, and
nothing stronger.

### 4.4. Mapping profiles

One client-level operation may produce several source-level statements. This
multiplicity is a property of the deployment, and not of the Gateway. It depends
on the version of the intermediary in front of the Data Source, on a connection
pooler, or on an object-relational mapper. A Gateway does not produce this
correspondence, so it cannot measure it.

The operator therefore declares a Mapping Profile. For each client-level
operation the profile covers, it states three things. It states the expected
set of source-level patterns, and that set is bounded. It states the bound on
their multiplicity.

It states the exclusion rules that apply before comparison (Section 4.5). The
profile carries a version identifier. An implementation serializes and digests
it as Section 3.3 describes.

The profile also declares the correspondence in time. The reason is the same as
for multiplicity: the operator knows it and the Gateway cannot measure it. The
profile states which clock each side uses. One clock stamps the Data Source's
snapshots, and the other stamps the Gateway's Receipts. The profile also states
the skew bound between the two clocks. Both statements come from the operator
and carry that standing under the rule below.

This holds for a declaration that both sides read one clock and that the bound
is therefore zero. Such a declaration is still a declaration. Two reads of one
clock do not happen at the same instant, and whether the remaining difference
matters is a judgement about the deployment. The rule below forbids any
presentation of that declaration as a measurement. This document also refuses a
third case: a bound of zero that holds because nobody looked. Nobody declares
that bound, and the reconciler reads it as agreement between the clocks.

A reconciliation result computed against a Mapping Profile MUST bind that
profile's digest. For each bound the result relies on, it MUST state whether the
bound is protocol-defined, measured, operator-declared, or undeclared. A result
MUST NOT present an operator-declared bound as a measured one.

The consequence is an upper limit. A coverage outcome computed against a
declared correspondence cannot be stronger than the declaration. Where the
operator makes the declaration, the outcome takes that standing, and the result
statement is required to show it.

Section 4.7 applies the same discipline to missing evidence. The rule here is
that same discipline, one layer up. A declaration presented as a measurement
claims too much. That holds whether or not the declaration happens to be true.

Where nobody declares a required multiplicity bound, the affected items are
indeterminate (Section 4.3). An implementation MUST NOT substitute a default
bound of one. Take any deployment that has a pooler in front of the Data Source.
On such a deployment, a one-to-one rule reports false observed-without-receipt
items. A silent default would make that error look like a finding.

An undeclared skew bound gets the same treatment, and for the same reason. An
implementation MUST NOT substitute a default of zero. Zero asserts that the two
clocks agree, and that assumption produces the false accusation this document
now guards against. An implementation MUST NOT substitute a bound of its own
choosing either.

Such a bound would decide the operator's question with a number the operator
never saw. Without the declaration, items whose only naming Receipt sits
outside the Window are indeterminate. The result reports the offset, and the
reader compares it against clocks that the reader knows and the reconciler does
not.

An offset can be larger than the Window itself. Without a declared bound, an
implementation MAY decline to offer the boundary as the explanation for such an
offset. The ground for that choice is that an artefact of the boundary cannot
exceed the interval the boundary marks. The choice concerns what an
implementation is willing to suggest in its report. It does not change the
outcome: the item is indeterminate either way.

### 4.5. Exclusions

Exclusion is a different kind of outcome from the other four. The comparison
produces matched, observed-without-receipt, receipted-without-observation, and
indeterminate. A party decides excluded before the comparison, and that decision
fixes what the comparison covers at all. Exclusion is therefore the outcome
through which someone can make a reconciliation come out clean, and it needs the
tightest reporting rules of the five.

Exclusion rules MUST be stated in the Mapping Profile, and the profile digest
therefore covers them. A result statement MUST report the count of excluded
items and the rule that excluded each of them. An implementation MUST NOT
exclude items by a rule that is not in the profile.

Without these constraints, a reader cannot tell a clean result from a result
that exclusion made clean. The digest is supposed to fix what the comparison
covered. One step decides what the comparison covers, and without these
constraints the digest does not cover that step. Session or catalog
housekeeping is a legitimate exclusion. The requirement is not that exclusions
stay rare. The requirement is that each exclusion is visible and that the
digest covers it.

The limit of what the digest achieves is worth stating, because a reader can
easily read more into it. The result carries the rule identifier, and that
makes the exclusion reproducible. A reader can see which rule removed each
item. The reader can confirm that the rule was in the profile the digest
covers. This does not establish that the exclusion was correct.

Take two rules. One removes session housekeeping. The other removes the very
statements an auditor came to examine. The digest covers both in the same way,
and both verify in the same way. The mechanism reproduces the decision, and it
does not judge the decision.

Consumers MUST NOT read an exclusion as justified because the digest covers it.
A result statement MUST NOT present the digest as evidence that the exclusions
were appropriate. Section 4.4 draws the same distinction between a declared
bound and a measured one. This section applies that distinction to the step
that decides what the comparison covers at all.

### 4.6. Result statement

The reconciliation result is a JSON object:

v:  coverage-reconciliation/2. The outcome names of coverage-reconciliation/1
   are not a subset of the names here. A /1 result that reports covered asserts
   more than the procedure establishes, and this version cannot express that
   assertion again. A consumer MUST NOT read a /1 result as a /2 result.

window:  Object with start and end, the two snapshot ts values.

source:  The common source identifier of the two snapshots.

snapshots:  Object with the start and end digests of the two snapshot
   structures.

receipts:  A digest that identifies the receipt set the reconciler compared. For
   chained receipt formats, the chain head digest and the sequence range are
   RECOMMENDED as the identifying material.

profile:  The digest and version identifier of the Mapping Profile that the
   comparison ran against (Section 4.4). The member is null when nobody declared
   a profile. With null, every item whose outcome depends on a multiplicity
   bound is indeterminate. So is every item whose only naming Receipt falls
   outside the Window, because with no profile there is no declared skew bound
   either.

bounds:  For each bound the comparison relied on, where that bound comes from:
   protocol-defined, measured, operator-declared, or undeclared. A result whose
   bounds are operator-declared states an outcome of that standing, and no
   stronger.

outcome:  invalid-window when the Window is unreliable (Section 4.3). Otherwise
   no-exceptions when every item is matched or excluded, and exceptions when any
   item is observed-without-receipt, receipted-without-observation, or
   indeterminate.

   The name states what the comparison left open. It does not state what the
   comparison proved. A result MUST NOT carry an outcome name that asserts
   coverage of the source-level activity. no-exceptions makes no such assertion.
   It says that the comparison produced no open item under the declared
   correspondence. That correspondence limits the statement (Section 4.4). So
   does the fact that the procedure assumes neither population to be complete.

items:  The list of items whose outcome is not matched. Each item carries its
   outcome. An excluded item also carries the profile rule that excluded it. The
   list holds pattern digests and not pattern text, for the reasons in
   Section 4.2.

counts:  The number of items in each outcome, including matched and excluded. An
   implementation MUST NOT aggregate indeterminate items into a proportion of
   coverage. An outcome that decides nothing cannot be averaged into one that
   decides. A percentage restores exactly the overclaim that this set of outcome
   names exists to prevent.

An implementation serializes and digests the result statement as Section 3.3
describes. The reconciling party is intended to sign it and register it
(Section 5). The reconciler SHOULD be operationally independent of the Gateway.
Where it is not, registration on a Transparency Service at least lets a third
party see that the result exists and when it appeared.

### 4.7. Semantics of the outcomes

An observed-without-receipt outcome states that evidence is absent. It does not
state why. Gateway bypass produces it. Receipt sink failure produces it. A
mismatch in the accounting scope produces it.

So does a Receipt that exists and names the object but carries a timestamp that
the Window's own two clocks put outside the Window. Section 4.3 removes that
last case from this outcome, rather than listing it as one more cause. This
document names the case here for a reason. An earlier revision of this document
listed the condition on the other side under receipted-without-observation and
not under this outcome. A reader who compares the two lists should see that
this revision corrects the omission.

That reader should not assume that the boundary distorts only one direction. A
result statement MUST NOT label such activity as an intrusion, a breach, or an
intentional act, and consumers MUST NOT present it as such. The value of the
mechanism is that it brings the condition to light. To attribute a cause is
investigation work, and reconciliation does not do it.

A receipted-without-observation outcome is likewise a statement about evidence,
and by itself it is not a fault. Several conditions produce the same shape in
the result as a receipt that describes activity that never occurred. A counter
reset at the Window boundary produces it. An intermediary that collapses
statements produces it.

An increment that lands outside the pair of snapshots produces it. An
implementation MAY treat this outcome as a failure condition under a policy of
its own. This document does not define it as one, because the shape of the
result does not distinguish the cases.

An indeterminate outcome is a result, and not a degraded pass. It MUST NOT be
resolved by assumption in either direction. It is neither counted as matched
because nothing contradicts it, nor reported as missing activity because nothing
confirms it. Someone may press an implementation for a single number, and the
implementation will then be tempted to fold indeterminate into a proportion of
coverage. That operation destroys the only property that separates this set of
outcome names from a plain "pass", and it MUST NOT be performed.

A verifier checks receipt signatures and chain integrity under the rules of the
receipt format in use. That work lies outside the scope of reconciliation, and
the procedure assumes it happened first. Reconciliation compares an
already-verified receipt set against the Data Source's account. It does not
verify that set again.

## 5. Registration on a Transparency Service

Both structures defined here are payloads for Signed Statements in the sense of
the SCITT architecture [RFC9943]. An Issuer signs the serialized structure and
registers the Signed Statement on a Transparency Service. For Transformation
Evidence, the Issuer is the Gateway operator. For a Coverage Reconciliation
result, the Issuer is the reconciling party.

The Issuer then obtains a Receipt in the SCITT sense. That Receipt proves that
the statement is included, at a position, in an append-only log. A party other
than the Issuer operates that log.

This document layers the two parts deliberately. The structures defined here
gain their audit value from registration in a place the Issuer cannot quietly
rewrite. SCITT already defines such a place, together with its trust model and
its verification procedures. This document therefore defines no
countersignature, no anchoring, and no log format of its own. This document's
mechanisms use digests to bind evidence to receipts. Registration leaves that
binding unchanged, because a digest covers the payload and not the envelope.

## 6. Security Considerations

Same-operator collusion. In many deployments, one party operates both the
   Gateway and the Data Source. Coverage Reconciliation is then worth less
   against that party. An operator with administrative access to the Data
   Source's account can suppress the counters themselves. The mandatory
   invalid-window rule (Section 4.3) turns a counter reset into a visible
   failure.

   Registration (Section 5) makes it detectable when someone suppresses results
   that were already issued. An operator who controls both accounts and never
   registers anything stays outside the reach of this mechanism. A deployment
   that needs assurance against the operator itself needs an accounting path
   the operator cannot write to. That is a property of the deployment, and not
   a property of the payload.

Counter manipulation.  An attacker who can reset or rewind the Data Source's
   counters could otherwise hide activity between snapshots. The MUST-fail rule
   exists for this case. A Window that contains a counter regression is reported
   unreliable in its entirety. Snapshot frequency bounds the exposure: with
   shorter Windows, a reset costs the attacker a visible failure sooner.

Declared correspondence as an attack surface. The operator writes the Mapping
   Profile (Section 4.4), and the profile decides both what counts as a match
   and what leaves the comparison before matching. An operator who can widen a
   multiplicity bound can absorb unreceipted activity into an expected range.
   An operator who can add an exclusion rule can remove that activity from the
   comparison entirely. This mechanism does not defend against such an
   operator, and nothing computed against a declaration can.

   What the mechanism does is to make the declaration part of the evidence. The
   profile is versioned. The result binds the profile's digest. The result
   reports exclusions with their count and rule. The result states that its
   bounds are operator-declared.

   A reader who trusts the result depends on the profile, and that dependency
   is visible instead of hidden. Registration (Section 5) lets a third party
   see the sequence of profiles an operator has declared. A silently edited
   profile would otherwise remove that property.

Digest agility.  Digests carry a prefix (Section 3.3), and an implementation
   MUST reject unknown prefixes. An implementation that accepted an unknown
   prefix as an opaque match would let an attacker route around the comparison.

Signature and key compromise.  Signing and registration come from the SCITT
   layer. Key management, revocation, and the consequences of Issuer key
   compromise are governed there, and not here. A compromised Issuer key voids
   the evidentiary value of statements under that key, as it does for any signed
   artifact.

## 7. Privacy Considerations

One rule shaped every structure in this document: evidence about protected data
must not itself become a channel for disclosure. Transformation Evidence
carries class names, action names, and counts, and never values. References to
requests and to patterns are digests, because query text and pattern text can
embed values and schema detail. Class names and counts do reveal that data of a
class was present in a result in a given quantity.

A deployment may find even that sensitive. Such a deployment can keep the
payloads private and register only their digests. The cost is that a
third-party audit then needs permission and is no longer a public act.

## 8. IANA Considerations

If this document progresses, it will request registration of two media types:
application/transformation-evidence+json and
application/coverage-reconciliation+json. Their content is the structures of
Section 3.2 and Section 4.6. This document requests no registrations at this
stage.

## 9. Implementation Status

_This section is to be removed before publication as an RFC, per [RFC7942]._

One implementation of both mechanisms exists: the Conarium gateway (TypeScript,
MIT license, @conarium-ai/core on npm). It has run in production at one site
since July 2026. Its receipts carry per-class masking counts as in Section 3.
Its conarium-reconcile tool implements the procedure of Section 4.3 against
PostgreSQL statement statistics.

The tool is a single file and does not depend on the package. A third party can
therefore run the reconciliation without trust in the implementation under
audit. Conformance test vectors ship with the package.

The implementation covers this revision only in part. The gaps appear here,
rather than waiting for a reader to discover them:

*  It reports observed-without-receipt, and since 0.2.23 it also reports
   receipted-without-observation. It does not yet emit the set of outcome names
   of Section 4.6 under those names, and its result carries no profile or bounds
   field.

*  Since 0.2.27 it reports indeterminate for the temporal case of Section 4.3.
   It uses that name, it uses its own exit code for the case, and it reports the
   offset that produced the outcome. It accepts a skew bound on the command
   line. It does not yet read one from a profile, because it does not implement
   profiles.

*  It does not implement Mapping Profiles (Section 4.4). Every bound it relies
   on is therefore undeclared. By the rule in Section 4.3, the items that depend
   on those bounds are indeterminate. The tool does not currently report them as
   such.

*  It removes session and catalog statements from the comparison and prints each
   excluded statement individually. Those rules are compiled into the tool
   instead of declared in a profile, so no profile digest covers them, as
   Section 4.5 requires.

*  Its exit codes are older than this set of outcome names, and they still do
   not map onto it. The codes stay unchanged on purpose. An exit code is a
   compatibility contract with existing deployments. To renumber the codes to
   match a revision of this document would break running installations, and it
   would only make a specification look implemented. The implementation added
   one code for the outcome above instead of renumbering. Existing callers do
   not notice such an addition, and it is not the mapping this bullet reports as
   absent.

Earlier revisions of this document described a clean reconciliation as
"covered". So did releases of that implementation up to 0.2.21. That word
asserted more than the procedure establishes. Release 0.2.22 corrected it in the
implementation, and revision -03 corrected it in this document.

The rule about time in this revision has the same history, over a shorter
period. The implementation admitted Receipts on an exact comparison across the
two clocks. A Receipt three seconds outside a two-hour Window therefore
produced observed-without-receipt and a message about a possible bypass. A
review of -03 on the SCITT mailing list raised the problem. Someone reproduced
it, and release 0.2.27 corrected it.

A reviewer then attacked the correction. A Receipt from the previous day named
the same object. That Receipt moved a real absence inside the Window into the
new outcome, and the implementation offered the boundary as its explanation. An
offset of twenty-three hours cannot support that excuse. Release 0.2.28 bounds
what the implementation is willing to suggest, which is the reporting choice
described in Section 4.4.

Both defects were in the implementation before they were visible in this
document, and nobody found either defect by reading this document. The first
came from review of -03 on the mailing list. The second came from an
adversarial review of the implementation. Someone commissioned that review
because the fix had loosened a default, and the author of the fix was not the
party who should clear it.

The tool's own output is what made the second of those sentences sayable. This
text did not yet exist. The document's part was smaller and later. The document
is where the correction has to be written down, so that the next implementation
does not have to be attacked to learn it.
